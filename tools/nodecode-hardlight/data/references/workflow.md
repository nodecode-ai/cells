# Workflow: from a real job to a recognizable interface

## Start with authority, not a style menu

Read the request, representative routes, existing tokens, assets and working behavior. Record the authority: **refinement** corrects execution without replacing identity; **extension** adds a surface to the established system; **redesign** changes the visual system but preserves product truth; **greenfield** establishes a new system. A missing design document is not evidence that a brand has no identity.

Write a task sentence: “A [person] needs to [action] using [object/information], and succeeds when [observable result].” Identify the first-visit question, repeat-use task, entry routes, actual content, irreversible actions and operational constraints. Record unknown facts rather than filling them with plausible copy. Separate a marketing promise from the application behavior needed to keep it.

**Exit evidence:** an authority decision, task sentence, scope boundary and list of missing facts/assets.

## Draw the routes before the rectangles

Load `hardlight_reference(topic="navigation")`. Map destinations, object hierarchy, global and local navigation, current location, direct entry and return paths. Write literal destination labels. Choose URL vs ephemeral state for filters, search, selected records and overlays. Include permission failure, unavailable content and task completion. Run the graph tool with actual intended links, but review semantic labels yourself: a reachable route called “More” may still be impossible to find.

**Exit evidence:** a small route table and task paths, including mobile topology and browser Back/Forward behavior.

## Explore competing structures

When direction is open, make three cheap concepts that answer the same task differently. Change at least two structural dimensions: opening composition, content order, navigation model, density, asset type or interaction premise. Three accent colors on one hero and card grid are one concept.

For example, a field-recording archive could be (1) an indexed publication with transcripts, (2) a map plus an equivalent location list, or (3) an audio-led collection with time-coded listening notes. Test what each makes easier and what it hides. Do not replace an approved refinement with an unsolicited three-way rebrand.

Use atlas grammars as compositional starting points, not presets or ranked recommendations. Inspect a current real site and a non-web/art reference when they can change a design decision. Record what transfers, what does not, and whether you actually saw the completed surface.

## Commit one design premise

Write a compact design brief containing:
- The subject-specific idea and the task it makes clearer.
- The opening arrangement: exact content, focal asset and useful action.
- Structural rules: alignment, grouping, density, sequence and navigation.
- Type roles, palette roles, material behavior and one distinctive gesture.
- An asset list with origin, rights, fallback, alt text and production status.
- A known tradeoff and the browser evidence that will challenge it.

The brief fails if an unrelated product name can be substituted without changing the composition. Inventiveness can come from original notation, content structure, material, typography or interaction—not necessarily animation or visual noise.

## Build the whole promise

Implement the primary task with real destinations and honest content. Then implement the state matrix from `hardlight_reference(topic="states")`. Every visible control must do a meaningful thing; remove unsupported actions or label a real limitation without pretending a fake action succeeded. Demonstration data must be marked illustrative.

Load typography, color and motion references as decisions arise, not as an undifferentiated context dump. Inspect a coherent first implementation at wide and narrow widths; fix material failures together. Test keyboard, touch, reduced motion, direct URLs and history. Do not polish a hero while its next destination is missing.

## Finish with the shipped system

Use `hardlight_reference(topic="review")` and `hardlight_reference(topic="browser")`. Extract only the decisions actually present in the working result using `hardlight_reference(topic="systems")`. Report artifacts, exercised paths and explicit gaps. Lint, screenshots and graph results are different evidence; none measures artistic superiority or substitutes for observing people perform the task.
